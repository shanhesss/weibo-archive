# 16. 取消同步 = 当场落「同步失败（已取消）」，在途那几条保留真实结果

- 日期：2026-10-15
- 状态：已接受（2026-10-15 用户拍板；同批修复 `clear_arch_state` 无限递归）

## 背景

用户反馈「点取消界面没变化，同步中的条数一直挂着」。排查出两个独立成因：

1. **`clear_arch_state(user_id)` 自递归**（weibo_server.py:1112，自 a6ec8ab / 2026-09-02 起）：
   else 分支把非空的 `user_id` 原样传回给自己 → 任何带 user_id 的调用必抛 `RecursionError`。
   后果三条：取消接口 500（前端只在 `ok` 时提示，看起来就是「点了没反应」）；
   取消/失败/模板读不到之后**瞬态从来没被清掉**；更要紧的是 `archive_worker` 里那两处调用
   不在 try 内，异常穿出线程 → **归档通道整个线程终止**，此后所有批次只入队不处理，
   「同步中」挂到进程重启为止。今早那批卡死的主因是这条，而不是 AI 超时。
2. **前端取消后不重渲染卡片**：轮询里「归档批次完成 → 刷卡片」的条件是 `yt > 0`
   （weibo_web.html:1682），而取消已把 `total` 清零 → 永远不触发 `loadPosts()`，
   卡片上的「同步中…」按钮原地挂着，要手动刷新页面才变。

## 决策

- **取消当场把状态落成可见的失败**：`api_yuque_cancel` 把该用户所有 `syncing/updating` 的行
  一次写成 `arch_state=''` + `arch_fail='已取消同步'`（常量 `CANCELLED_MSG`），
  复用既有渲染 → 卡片立刻显示**同步失败**并带【同步】重试按钮；已归档过的行显示「更新失败」。
  不再只是静默清空瞬态（清空 = 回到「待归档」，用户无从知道是没跑还是跑坏了）。
- **在途那几条保留真实结果**：批内最多 2 路是 urllib 阻塞调用，纯标准库下硬中断要动 socket，
  代价与风险都不值。它们跑完后照常写回 —— 成功即「已归档」，失败记真实原因，覆盖「已取消同步」。
  与按钮标题「停止剩余同步，已归档的保留」一致。等待队列里的条目取消时即清空，不再提交。
- **worker 的取消收尾不再整批清瞬态**（run_archive 的 cancelled 分支去掉 `clear_arch_state`）：
  落态已由取消接口当场完成，再清一次只会误抹掉「取消后又立刻点同步」那一批的「同步中」。
- **修 `clear_arch_state` 按 user_id 过滤**，归档线程不再因此死亡。
- **前端取消后强制刷卡片**，并把接口返回的失败原因 toast 出来（不再静默）。

## 备选方案

- **只修递归、不改取消语义**：界面会恢复「能点动」，但没跑到的条目回到「待归档」，
  用户看不出这批到底同步没同步——违背「任何时刻页面出现看不懂的状态视为 bug」。否。
- **硬中断在途请求**（持有 response 句柄、取消时关 socket）：能少等最多 300s，
  但依赖 urllib 私有结构、异常形状不可控。否。
- **取消后一律算失败、丢弃在途结果**：白白浪费已消耗的 AI 额度，且语雀里已建成的文档
  与本地状态对不上。否。

## 后果

- 「同步失败」多了一种人话原因：`已取消同步`，悬浮可看、可单条重试。
- 取消后进度条归零（`total=done=0`），worker 收尾时显示「已取消：已归档 N 条，其余未同步」。
- 归档通道线程不再因一次取消 / 一次模板读取失败而永久失能；这条是今早卡死的真根治。
- ADR-0013 / ADR-0015 讲的降级与本 ADR 的取消互不影响：取消只停「剩余条目」，
  已判死的 AI 配置仍在同批次内继续生效。
- 同批顺带修一处：`yuque_mount_doc` 原来只 `except ApiError`，语雀 toc 返回形状意外时
  抛 `AttributeError`，把**已经建好的文档**误判成「同步失败」——与「挂载是锦上添花、
  挂不上不拦截归档」的既定语义相反。改为 `except Exception` 返回未挂上。
