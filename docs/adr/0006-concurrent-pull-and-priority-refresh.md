# 6. 并发拉取 + 批量更新优先级 + 最早微博时间

- 日期：2026-08-20
- 状态：已接受

## 背景

早期设计（ADR-0002 背景）为串行拉取：单 worker 一次拉一个博主，批量更新与拉取共用同一队列，更新排在长拉取后面。用户提出：多账号同时拉取、手动勾选更新优先执行并显示进度、展示博主最早微博时间。

## 决策

- **并发拉取**：共 3 个 worker —— **最多 2 个同时拉博主**（独立断点/进度/可暂停，各自 6-10 秒页间间隔），第 3 个 worker **专留给批量更新**。并发 2 路 ≈ 每 6-10 秒 2 个请求，限流风险可控；不再提高上限（432 概率随并发上升）。
- **批量更新优先级**：更新走**独立队列 + 专职 worker**，进队即跑，**不等待、不暂停正在进行的拉取**（两边并行、互不阻塞）。
- **更新进度**：批量操作条显示「更新中：已更新 X 条 / 待更新 Y 条」，X 逐条递增；完成后提示并刷新列表。
- **最早微博时间**：博主行昵称下新增一行展示该博主**当前已拉数据中时间最早一条**的发布时间（到日），**实时计算**（`MIN(created_ts)`），不落库 —— 与数据一致且自动更新。

## 后果

- 拉取吞吐翻倍；若遇 432 频率限制，靠现有退避与暂停兜底。
- 批量更新即时执行，进度可见，长拉取不再拖累手动操作。
- 最早时间随数据变化自动重算（删除旧数据后最早时间会上移，属预期）。
