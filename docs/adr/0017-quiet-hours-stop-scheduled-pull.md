# 17. 自动拉取静默时段：全局一份、按北京时间算术判断、到点顺延不打断手动

- 日期：2026-10-15
- 状态：已接受（2026-10-15 用户拍板，逐条确认 20 项决策）

## 背景

诉求：定时拉取要能设「停止拉取时段」，且支持多段。动机是夜里不该让小号持续打微博接口。

排查现状时发现三件必须先定的事：

1. **现有调度是「先落时间再入队」**（`schedule_worker`，weibo_server.py:1021 原行号）：
   一旦到点就无条件把 `sched_last` 刷成当前时间。如果撞上时段直接跳过，那一轮就**永久错过**，
   下个周期重新起算 —— 会出现「设了 8 小时间隔 + 夜间停 8 小时，白天可能整天不拉」。
2. **容器时区没有保证**：`deploy/cloudbase/Dockerfile:21` 只设 `ENV TZ=Asia/Shanghai`，
   镜像是 `python:3.12-slim` 且**没有装 tzdata**。缺 `/usr/share/zoneinfo` 时 glibc 静默回落 UTC，
   那么「按几点几分停」会整体差 8 小时，而线上没有任何免登录端点能观测服务器墙钟（只能下载快照库比对）。
3. **调度完全没有时段概念**，且触发后 `enqueue_all` 一次性把全部博主入队、此后不再回头检查；
   中断原语（`STOP` 事件）不分任务来源，`STOP` 置位后 `run_sync` 开头还会 `ev.clear()`，
   所以「只打断正在跑的」挡不住静默时段里陆续开跑的排队任务。

## 决策

### 语义

- **顺延，不是跳过**：时段内到点既不触发、也**不刷 `sched_last`**，时段结束后靠既有的
  「超间隔自然补跑」机制立刻跑一轮。为此新增 `schedule_once()`（一个节拍做的事），
  `schedule_worker` 只保留节拍与兜底 —— 顺带让这段逻辑可测。
- **时段开始要叫停在跑的定时任务**，不是只挡新轮次：诉求本身是「停」。
  响应延迟 = 调度节拍 20 秒，中断粒度到单条博文（页间仍有网络等待），非瞬时。
- **叫停走「暂停」不走「取消」**：保留 `next_page` 断点，时段结束后接着拉，已拉数据不丢。
  落库 state 仍是 `paused`，只有 note 换成「静默暂停，时段结束后自动继续」
  （卡片直接显示 note，因此界面上是「静默暂停」，不新增状态档）。
- **只约束自动，手动一律不受限**：手动单卡拉取、一键全部、重拉全量照旧；
  进入时段**也不打断手动发起的那一轮**（否则与「手动不受限」自相矛盾，
  用户会看到「我自己点的被系统停了」）。
- **只挡定时拉取**：语雀归档、快照、每日清理照常 —— 诉求是微博接口，不是全站停业。
- **管理员不豁免、无例外名单、无临时放行开关**：全局规则带后门就会变成给自己开后门；
  管理员要临时补数据用手动拉取，这已经是现成的放行通道。

### 归属与时区

- **全局一份**（`kv` 键 `sched_stop_windows`，JSON 数组 `[{"start":"22:00","end":"06:00"}]`）：
  管理员在后台配，所有用户受同一约束；定时开关/间隔仍按用户存 `user_kv`（不变）。
  注意 AGENTS.md/CONTEXT.md 原写「定时拉取存 kv 表」与代码不符，本次一并纠正为 `user_kv`。
- **时间基准写死东八区，用 epoch 算术**：`bj_minutes() = time.gmtime(time.time() + 8*3600)`。
  不用 `zoneinfo`（Python 3.12 在 Windows 本地开发会 `ZoneInfoNotFoundError`，而项目硬约束纯标准库零依赖），
  也不赌镜像带不带 tzdata、不依赖容器 TZ —— 本地与线上行为必然一致。
- **在不在时段内由后端判断**：`/api/state` 新增 `stop_windows`（文本数组）与 `in_stop_window`（布尔）。
  基准既然固定东八区，判断就必须同侧，不能让访客设备时钟/所在时区决定用户看到的状态。
  `schedule` 字段形状**保持不动**（被 `smoke_test.py:650` 严格相等锁死）。

### 边界与校验

- 支持跨午夜（`start > end` = 当天开始至次日结束）；重叠段不阻止，判断天然按并集生效。
- 段数上限 5（`STOP_WINDOW_MAX`）；`start == end` 一律拒绝并提示「等于全天不拉，请直接关掉定时」。
- **写入严格校验报错、读取容错跳过坏段**（`stop_windows()` 丢掉非法项，其余照用），与 `ai_pool()` 同口径。
  已知不一致：`sched_cfg()` 对间隔是静默夹回、`api_schedule()` 是报错，新字段选后者 + 读取容错。

### 界面

- 管理后台在「AI 归档服务」与「数据备份」之间新增区块「自动拉取静默时段」，
  照 AI 池范式：列表行（含「次日」标注）+ 内联表单两个 `<input type="time">` + 添加/删除，
  即时保存、成败都重拉对齐。`GET/POST /api/admin/stop_windows`，`_admin()` 门禁。
- 用户侧在定时弹窗内只读展示（未设置则整块不显示，符合「默认即可用」），
  正处于时段时追加一句「现在正处于静默时段，自动拉取已暂停」。
- 主界面提示行 `#taskHints` 在静默期内加一句「自动拉取静默时段中（北京时间 …），时段结束后自动接着跑」。
  这条是必要的：进入时段会让多个卡片同时从「拉取中」变「静默暂停」，光靠卡片注释撑不住。
- 顶栏「定时·每 N 分钟」按钮**不随时段变文案**（高频按钮忽变像故障）。

## 备选方案

- **跳过本轮**（时段内照刷 `sched_last`）/ **视为过期但不追**：都会让数据陈旧到用户无法预期，否。
- **只挡新触发、在跑的跑完**：与「停」的字面诉求相反，夜里照样打接口，否。
- **叫停走取消语义**（丢断点）：时段打断不该让已拉一半的进度作废，否。
- **一律打断**（含手动那一轮）：与「手动不受限」直接冲突，最容易被当成 bug，否。
- **按用户各配一份**：与「平台级安静时间」的诉求不符，且会出现「定时按用户、停时段按全局」的分裂心智，否。
- **管理员豁免 / 例外名单 / 全局临时放行开关**：有了「手动不受限」再加后门就是重复的门，还要管自动过期，否。
- **跟随容器 TZ**（沿用 naive `datetime.now()`）+ 补 tzdata：本地开发与线上可能不一致，且要赌镜像内容，否。
- **时区做成可配置项**：个人项目里没人会去改，多一个必填概念，否。
- **新增 `quiet` 状态值**：为一条文案牵动 `STATES`、前端映射与既有测试，代价不成比例，否。
- **一行文本框填 `01:00-07:00, 12:30-13:00`** / **固定 5 对时间输入框**：前者违反零术语，
  后者 10 个输入框更啰嗦且上限钉死，否。
- **回填历史时间戳（若实测容器真是 UTC）**：判断哪些值是 UTC 写的、切点在哪都容易出错，
  写坏不可逆，收益只是旧记录对齐，否。

## 后果

- 定时拉取的「错过补偿」现在有两个来源：进程重启、静默时段 —— 走同一条 `sched_last` 未刷新路径，
  不新增补偿逻辑，也不会因时段碎片化而跑得更频繁（补跑仍要求「距上次超过间隔」，时段只让它变晚）。
- 短时段（如午休 30 分钟）反复打断长尾博主不会丢进度：每次都是保断点暂停，最终一定拉得完。
- 用户手动点【继续】仍会立刻接着拉 —— 时段只约束自动行为，这是有意的。
- **线上容器时区已实测确认正常**（2026-10-15 下载快照库比对）：`now_str()` 写出的 `last_synced_at`
  与同一时刻 `sched_last`（epoch）换算的北京时间一致（21:49:11 vs 21:49:03），
  即 `python:3.12-slim` 自带 zoneinfo、`ENV TZ` 生效，历史墙钟无需修正。
  即便如此，本功能的判断仍走显式 epoch 算术：不依赖镜像内容，本地开发与线上必然一致。
- 界面新词：「自动拉取静默时段」（标题带「北京时间」）、「静默暂停」，已收进 CONTEXT.md。
