# 15. 归档降级按错误类型分流：连不上的中转在本批次内拉黑

- 日期：2026-10-15
- 状态：已接受（2026-10-15 用户拍板方案 B；取代 ADR-0013 的「不区分错误类型、不做熔断」口径）

## 背景

2026-10-15 上午 DeepSeek 中转故障，一批语雀归档长时间停在「同步中」不动。排查确认超时都在，
但被重试结构乘成了事实上的无界等待：

- 单条 AI 调用超时 `SYNC_TIMEOUT=300s`，语雀 OpenAPI 20s，不存在裸调用；
- 但单条 = 外层 2 轮 × 整池家数 × 300s。主用挂掉时**每一条**都要先白等满 300s 才轮到备用；
  整池全挂则单条 20 分钟；批内只有 2 路并发，几十条即数小时的「同步中」。
- 外层那第 2 轮的初衷（ADR-0013「输出格式漂移重试 1 次」）是防漂移，但实现只 `except ApiError`，
  连不上、超时也照样再跑一轮——服务宕机时纯粹把等待翻倍。

ADR-0013 当年「刻意简化为不区分原因、无熔断」的前提是「个位数用户、低频后台归档，复杂度不值得」；
现实代价是主源故障期间整批归档不可观察地卡死，比复杂度更不值得。

## 决策

- **AI 失败分三类**（两个 `ApiError` 子类）：
  - `AiTransportError`——连不上 / 超时 / 网关 5xx / 返回不是 JSON：这家此刻不工作；
  - `AiFormatError`——输出不合契约（格式漂移 / 空内容 / `max_tokens` 截断）：这家活着，是模型输出问题；
  - 其余 `ApiError`（4xx、鉴权失败、限流、200 体内带 error）：既不拉黑也不额外重试。
- **批次内拉黑**：一条链路上出现过 `AiTransportError` 的配置下标记入本批次的 `dead` 集合，
  后续条目直接跳过这家（原因写「本批次已连不上」进汇总）。**作用域只有当前批次**：
  批次结束集合即丢弃，下一批重新现试；不做跨批熔断、不做健康检查、不记故障次数。
- **第 2 轮只留给漂移**：整链全败时，只有本轮出现过 `AiFormatError` 才抛可重试类型、
  让 `archive_one` 再走一轮；纯传输类失败立即放弃这一条，不再等第二遍超时。
- 超时值维持 300s 不动：慢而正常的思考型长文生成要靠它兜住，卡死的根因是重复付费而非超时过长。

## 备选方案

- **只修重试分类**（不动熔断口径）：单条从 600s 降到 300s×家数，但主源挂掉时每条仍各交一次税，
  几十条批量照样一小时以上。否。
- **把 `SYNC_TIMEOUT` 降到 120~150s**：线性缩短等待，但会误杀慢而正常的长文生成——
  当初正是为此从 120s 调到 300s（ADR-0014）。否。
- **跨批次熔断 / 健康检查**：状态要持久化、要恢复探测，复杂度与实际收益不匹配。否。
- **流式调用（stream:true）**：治的是「读不到字节就没法判断死活」，ADR-0014 已列为后续可选项，
  本次不做。

## 后果

- 主源故障期间：整批只在**第一条**付一次 300s，之后秒切备用；池内全挂时整批快速失败并给出
  各家原因，而不是缓慢卡死。
- 用户可见的失败文案不变（仍是「AI 归档服务全部没成功（各家原因）」），
  只是「连不上」的家在后续条目里显示为「本批次已连不上」。
- 一家中转在批次中途恢复不会本批内被重新启用——要到下一批。接受：批次可取消、可重跑。
- ADR-0013 的其余内容（有序池、界面增删改/排序、掩码红线、判定「开通」口径、
  整链全败才向用户报错）不变；其「不区分错误类型即换下一家、不做熔断」由本 ADR 取代。
