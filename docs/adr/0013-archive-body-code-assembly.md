# 13. 归档生成提速：正文由代码拼装、AI 不抄原文；成功次数跟条目稳定 ID

- 日期：2026-09-28
- 状态：已接受（与云托管线 ADR-0014 同结论，两条产品线各持一份；取代 ADR-0012 的「按 备注名|地址|模型 归并」计数口径）

## 背景

归档慢且偶发失败，诊断信息定位到两个结构性原因：

1. 生成契约要求 AI 把「微博正文」**原样抄全文**进 BODY——输出 token 一大半是纯搬运，
   耗时与输出长度成正比；
2. 思考型/编码模型先思考再吐正文，4000 的 `max_tokens` 被思考占满、正文没吐出来
   （`stop_reason=max_tokens` 空返回），旧 240s 读超时也误杀慢而正常的请求。

另有一个计数缺陷：成功次数按「备注名|地址|模型名」拼 key 归并，只改模型名也会清零计数。

## 决策

- **正文代码拼装**：提示词契约改为「微博正文」章节只输出占位符 `{{微博正文}}`，
  生成后由 `_fill_body()` 用库里原文替换；模型没按契约给占位时兜底在文末追加该章节。
  归档文档内容不变（正文本就是原样保留），AI 只读输入不抄输出，生成量约降一半以上。
  模板 `yuque-sync-template.md` 同步改写。
- **调用参数放宽**（先行落地）：AI 调用超时 240s → 300s；`max_tokens` 4000 → 8000；
  `stop_reason=max_tokens` 且无正文时单独报「输出被长度上限截断」。
- **成功次数改按条目稳定 id 归并**：池条目在新增 / 旧三键迁移 / 首次读取补发时生成 `id`，
  编辑任何字段（含模型名）都保数，仅删除条目时计数随条目消失。

## 备选方案

- **流式调用（stream:true）**：不真的变快，只防超时误判，纯标准库解析 SSE 有成本——留作后续可选项。
- **主副并发竞速**：更快但双倍耗额度，违背主备兜底初衷，否。
- **提示厂商关闭思考**：各家参数不一、不支持即 400，不做。

## 后果

- 「同步模板」的用户可见语义微调：正文章节由系统填入全文（模板里显示为占位符）。
- 旧格式归档再同步时按新契约重新生成，结果一致。
- ADR-0012 中「按 备注名|地址|模型 归并」的计数口径由本 ADR 取代。
