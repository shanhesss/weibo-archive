# 12. AI 归档服务配置池：多家中转有序主备，任一失败即换下一家

- 日期：2026-09-26
- 状态：已接受（与云托管线 ADR-0013 同结论，两条产品线各持一份；取代 ADR-0011 的「单一中转」表述；其中「成功次数按 备注名|地址|模型 归并」已被 ADR-0013 改为按条目稳定 id）

## 背景

ADR-0011 把语雀归档定为直调**一家** Anthropic 兼容中转（地址/密钥/模型名三项，全局 kv 配置）。
单一中转有两个现实风险：服务不稳或配额耗尽时归档整体不可用、无兜底；用户手里往往备着
多家（主用 + 手动买过的备胎），希望网页上能自行维护，而不是只有一个填法。

## 决策

- **配置池**：kv 键 `ai_pool` 存 JSON 有序数组，每项 `{name, base_url, key, model, enabled}`，
  数组顺序即优先级（第一个为主用）。旧全局三键（ADR-0011）在首次读取时一次性迁移成
  池里的第一项（名「主用」），迁移后三键清空，池为唯一事实源。
- **降级策略（刻意简化）**：每次生成都**现走一遍链**——从主用起依序尝试，**任何失败
  （不区分错误类型）即换下一家**，整链全败才向用户报错并附各家原因。**不做熔断、
  不做健康检查**，不为上一次失败拉黑任何一家。
- 单条微博的重试语义不变：输出格式漂移重试 1 次（共 2 轮），每一轮都整链走一遍。
- **成功计数**：每家中转累计生成成功次数，落 kv `ai_stats`（按 备注名|地址|模型 归并，
  改这三项等于换身份重新计数），管理列表行末展示——判断哪家在干活、哪家形同虚设。
- **空响应带诊断**：中转把错误装进 200 响应体、返回非 Anthropic 形状（OpenAI choices）、
  或真·空内容时，错误信息附带 stop_reason 与响应摘要，便于定位备用偶发的空返回。
- **管理界面**：管理后台「AI 归档服务」从一行输入变为有序列表——添加 / 编辑（密钥留空
  = 保持原值，勾选才清除）/ 删除 / 停用·启用 / 上移·下移；读取接口只回掩码，
  任何界面与日志永不回显密钥原文（继承 ADR-0011 红线）。
- 判定「开通」的口径不变：池里**至少一项启用且地址/密钥/模型名三项齐全**才可用，
  否则同步入口拦截并提示联系管理员。

## 备选方案

- **按失败类型区分降级**（429/5xx 才换家、格式漂移只重试同一家）：用户明确否掉
  ——「不做这么复杂，只要没成功就是失败」。
- **熔断 / 健康检查 / 故障计数**：个位数用户、低频后台归档，复杂度不值得。
- **按用户各配中转**：归档消耗的是全局配额，凭证管理保持全局一份，否。
- **env / 配置文件承载多中转**：破「管理员网页可自助维护」的目标，否。

## 后果

- 整链同败一次的耗时 = 各家超时之和（最坏 3×240s），发生在后台归档线程，用户只见
  最终失败原因，可接受。
- 池为 kv 里的 JSON，无 schema 变更，随打包版 `weibo.db` / 服务器库一并备份。
- ADR-0011 中「AI 中转地址/密钥/模型为全局配置」的表述由本 ADR 取代（单一配置 → 有序池）；
  其余（直调 API、TITLE:/BODY: 契约、掩码红线、语雀 token 按用户）不变。
