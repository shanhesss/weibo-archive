# 18. 挂载就绪守卫：读不到快照不再等于「云端没有」，等不到就拒绝启动；同时把夜间副本降到 0

- 日期：2026-10-18
- 状态：已接受（2026-10-18 用户拍板：修挂载竞态 + 控制台改「自定义 + 定时扩缩容」08:00-21:59 常驻 1、其余最小 0）

## 背景

**事故**：一次冷启动后，云存储里的快照位 `weibo/weibo.db` 被一份空库覆盖。三步成因（用户复盘给出）：

1. **cosfs 挂载延迟**：容器重启后 cosfs 要重新建立 FUSE 挂载，挂载完成之前挂载点表现为一个**空目录**。
2. **启动检查过早**：`cos_restore()` 只看 `os.path.exists(/mnt/weibo/weibo.db)`，此刻文件当然不存在。
3. **触发创建逻辑**：判定「没有快照」→ 按新库启动 → 周期快照 / 停止信号快照照写 → COS 的 PUT 是覆盖式，
   同路径旧对象被空库冲掉。

原代码的兜底注释写着「恢复失败仍照常起（宁可空库也要保证服务起得来）」——正是这条策略把
「可用性优先」换成了「数据完整性归零」。在 `min=0`（缩容到 0 后冷启动是常态）的形态下，这个竞态被踩中的概率显著上升。

## 决策

### 挂载就绪守卫

- **新增 `cos_mounted()` 区分「还没挂上」与「云端真没有」**：两个信号取或 ——
  ① `os.stat(COS_DIR).st_dev != os.stat(运行库所在目录).st_dev`（真挂上后是另一个文件系统，
  未挂载时挂载点只是个普通目录、和容器本地盘同设备）；② `/proc/mounts` 里命中该路径**或其祖先**。
  ⚠️ 基准必须是运行库所在目录（本地盘），挂载点匹配必须是前缀：平台挂在 `/mnt`、
  而 `WEIBO_COS_DIR=/mnt/weibo`，拿「父目录」或「精确路径」比会在生产上**恒判未就绪**、
  直接把服务锁死（这条在上线前自查时发现并纠正）。
- **新增 `cos_wait_mount()`**：启动时最多等 `COS_MOUNT_WAIT=45` 秒（每 3 秒一次）。上限压这么短是因为
  再长会拖住部署健康检查、诱发 `create_failed`。
- **守卫自带应急出口**：环境变量 `WEIBO_COS_MOUNT_GUARD=0` 可整体关掉判定（恢复与写入两侧同时失效），
  用于「判据在某个平台版本上误判导致起不来」时的运维接管；默认开，不是常规配置项。
- **等不到就绪 → `cos_restore()` 返回 False → `main()` 直接 `sys.exit(1)`**：
  不带着空库起来，交给平台重启重试。**「两处皆无」只在挂载确认就绪后才允许判定为首次部署**。
- **恢复过程中出错同样拒绝启动**（原来只是打一行日志继续起）：云端明明有快照却没拉成功，
  起来必然覆盖它。
- **`cos_snapshot()` 写入前也要 `cos_mounted()`**：未就绪就跳过这一轮并返回人话错误
  （运行中挂载掉落时不再往假目录写；本地库还在，等下轮挂载恢复再写）。
  顺带保证不再在未挂载时 `os.makedirs(COS_DIR)`，避免把普通目录伪装成挂载点。
- 未配 `WEIBO_COS_DIR` 的本地形态完全不受影响（`cos_restore()` 直接返回 True）。

### 副本数与运行模式归控制台

- 部署命令**去掉 `--min-num/--max-num`**（README 与 `pack.sh` 的提示同步改），
  因为 CLI 带上这两个参数会把控制台的运行模式设置覆盖掉；部署后用
  `cloudbase cloudrun detail` 复核 `MinNum/MaxNum`。
- 最大实例数**恒为 1**：两个容器各有独立的本地盘 `weibo.db`，却都往同一个快照位写 →
  后写的覆盖前一个，落在另一实例盘上的写入永久丢失；会话又存在各自库的 `sessions` 表里，
  跨副本会随机 401。要多副本必须先把数据层换成共享数据库，不属于本次范围。
- 夜间 `min=0` 的取舍：官方文档明确告诫「定时任务无法通过外部请求维持，最小实例数不能设为 0」
  且「不要在请求处理程序之外起后台线程」——本应用两条都踩（`schedule_worker` 等全是进程内线程）。
  用户仍选择用缩到 0 换空闲不计费，因此把语义讲明白：**夜间不是「静默」而是「不存在」**，
  定时拉取、cookie 复验、快照全都不跑；早上第一个请求触发冷启动（含从挂载盘拷回整库，几秒到十几秒），
  随后调度线程发现「距上次已超过间隔」自然补跑一轮 —— 与 ADR-0017 的顺延机制同一条路径，无需新增代码。
- 应用内的静默时段（ADR-0017）**保留**：它管的是白天里的自定义停拉窗口（午休、活动时段等），
  与控制台的副本计划互不冲突。

## 备选方案

- **启动时无条件 sleep 固定秒数**：拍脑袋的魔法数字，挂载快了就白等、慢了照样翻车。否。
- **区分不了就只告警、照常起服务**：就是这次的事故路径。否。
- **靠「写快照前先读一次云端文件大小」自检**：多读一次并不能证明挂载已就绪（空目录读不到任何文件），
  而且把安全性建立在文件大小猜测上更脆。否。
- **`min=0` + 外部云函数定时唤醒**：个人版云函数超时锁 3 秒，只能「戳一下」不能陪跑；
  唤醒链一断（配额、超限停服、定时器漏跑）定时静默失效且无告警。控制台的定时扩缩容达到同样省钱效果且少一个组件，否。

## 后果

- 冷启动若撞上挂载未就绪，表现为**实例起不来、平台重启重试**，而不是「起来了但把数据清空」——
  可用性换数据完整性，方向是有意的。日志会打印明确原因（`挂载盘 … 在 45 秒内未就绪，拒绝启动`）。
- 手动快照接口 `POST /api/admin/snapshot` 在挂载未就绪时会返回「挂载盘未就绪，本次快照已跳过」，
  不再静默写一份假的「成功」。
- 周期快照失败时不更新 `last` 签名 → 下一轮自动重试，无需额外补偿逻辑。
- 冒烟测试新增 4 条挂载守卫断言；既有的 seed 恢复用例改为显式打桩「挂载已就绪」
  （它测的是就绪之后的恢复优先级，普通临时目录在新守卫下会被判未就绪）。
- 夜间缩 0 后，「上次同步时间」在早上第一次唤醒补跑前会显得很久不动，属预期；
  若某天觉得这个观感比省下的钱更烦，把控制台最小实例调回 1 即可，无需改代码。
- **`min=0` 的省钱效果受「有人开着页面」直接限制**（2026-10-19 实测踩到）：前端登录后每 2.5 秒
  轮询一次 `/api/state`（weibo_web.html:2767），而云托管的缩容判定是「30 分钟内无请求」——
  页面只要开着，计时就永远清零，实例常驻不缩。排查时容易误判成「定时扩缩容没生效」。
  另外「定时扩缩容」规则是按时段设定实例数，白天那条设成 1 就意味着白天不缩，
  想在白天验证缩 0 必须先把该时段的数值改掉。
