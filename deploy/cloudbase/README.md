# 微博存档工具 · 腾讯云托管（CloudBase CloudRun）部署

本工具已从轻量云服务器迁到 **CloudBase 云托管**（决策见 `docs/adr/0011`、`docs/adr/0012`）。
本手册即唯一现行部署文档；旧轻量服务器链（`deploy/README.md` + install.sh + nginx）在本分支
已整体删除，历史形态保留在 `main` 产品线。

> **产品线**：本分支 `cloudbase-cloudrun`（云托管容器形态）与 `main`（本地 exe / 云服务器形态）
> 永久平行、互不合并；exe 打包、vbs 启停、tar 部署等本地线文件只在 main 有。

> **隐私打码**：本手册中环境 ID、域名一律为占位符（`prod-xxxxxxxxxxxxxxxx`、
> `<你的备案域名>`）。自己部署时先替换成自己的值：环境 ID 用 `cloudbase env list` 查看，
> 默认域名在控制台「云托管 → 服务详情 → 自定义域名」查看。

- 环境：`prod-xxxxxxxxxxxxxxxx`（个人版即可，上海）；服务名 `weibo-archive`（可直接沿用）
- 本机前提：已安装并登录 CloudBase CLI（验证：`cloudbase env list` 能列出环境）
- **铁律不变**：`weibo.db` 绝不进 git、绝不进镜像。数据只走「对象存储挂载盘快照」通道（见下）

## 架构一页纸（为什么长这样）

```
浏览器 ── HTTPS ── 云托管网关（60s 超时 / 你的备案域名的 /weibo 路由）
                     │
              云托管实例（副本恒定 1，容器本地盘跑真 SQLite）
                     │  weibo_server.py（纯标准库，后台线程跑拉取/归档）
                     │
              每 5 分钟 + 收到停止信号时：sqlite backup → 原子拷到
                     /mnt/weibo/weibo.db（对象存储挂载盘）
新实例启动：本地无库 → 优先从 weibo/seed.db 播种（一次性）、
                     否则从 weibo/weibo.db 拉回再打开
```

- **为什么副本 min=max=1**：定时拉取/归档快照靠常驻后台线程；同时杜绝两个实例同时写库。
- **为什么快照式而不是直接挂载跑库**：个人版开不了 VPC → CFS 不可用；对象存储挂载不支持
  文件锁/随机写，SQLite 不能直接跑在上面。快照式已闸门实测（2026-09-26：90MB 快照 2.9s、
  恢复 182ms、跨重部署 sha 一致、integrity ok）。
- **60s 网关超时不伤功能**：所有耗时动作（拉取、归档）都在后台线程，HTTP 请求只做入队/查询。

## 首次部署（一次性，含控制台操作）

控制台侧（浏览器登录 云开发控制台 → 你自己的环境）：

1. **云函数/云托管 → 创建服务** `weibo-archive`，规格选最小档（0.25 核 0.5G 起，不够再加）。
   创建后不用管它，先用 CLI 部署上去。
2. **服务详情 → 存储设置 → 对象存储挂载**：挂载目录 `/mnt`（不能挂 `/`、`/app` 等保留路径）。
   ⚠️ **挂载配置只在「下一次部署」生效**——改完挂载必须重新部署一次，否则实例会静默写到
   容器本地的假 `/mnt`（闸门实测踩过的坑）。

CLI 侧（仓库根，git-bash）：

```bash
bash deploy/pack.sh                      # 产出 cloudbase-dist/（代码 + Dockerfile，无库）
printf 'n\ny\n' | cloudbase cloudrun deploy -e prod-xxxxxxxxxxxxxxxx -s weibo-archive \
  --source cloudbase-dist --port 8766 --min-num 1 --max-num 1 --force --wait
```

> `printf 'n\ny\n'` 是应答 CLI 的两个交互提示（不切流量 / 确认覆盖进行中的部署）；
> `--force` 并不会跳过它们。

## 数据迁移（把已有库播种进快照通道）

适用场景：从旧服务器/本机迁过来，手上有一份 `weibo.db` 留档（本次迁移实例为 86MB / 约 8 千条）。

1. 先按上面完成首次部署 + 挂载配置（此时线上是空库在跑，没关系；若挂载是刚配的，
   再重新部署一次让挂载生效）。
2. 把留档库**改名为 `seed.db`**，云开发控制台 → **存储管理** → 上传到 `weibo/` 目录
   （对应实例内 `/mnt/weibo/seed.db`；`weibo/` 不存在就手动建目录）。
   ⚠️ 不要直接传成 `weibo.db`——快照位每 5 分钟会被（空）库覆盖，播种会被冲掉。
3. 再重新部署一次 → 新实例启动时**优先从 seed.db 恢复**（一次性消费，用完自动改名
   `seed.db.used`，之后正常走快照位）。
4. 验证：日志打印 `已从云存储快照恢复库：/mnt/weibo/seed.db（约 N 千万字节）`；打开
   `https://<你的备案域名>/weibo/` 登录 admin，微博总数应与迁移库一致。
   跑 5 分钟后确认存储里 `weibo/weibo.db` 被真实库覆盖，`seed.db.used` 可删可留。

之后日常运行会不断覆盖快照位——**`weibo/weibo.db` 即线上数据的最近备份**，
随时可在控制台下载回本地（下载前最好对照页面上的微博数，快照最长滞后 5 分钟）。

## 日常升级（只改代码）

```bash
bash deploy/pack.sh
printf 'n\ny\n' | cloudbase cloudrun deploy -e prod-xxxxxxxxxxxxxxxx -s weibo-archive \
  --source cloudbase-dist --port 8766 --min-num 1 --max-num 1 --force --wait
```

- 旧实例收到停止信号时会**自动做最后一次快照**（SIGTERM 处理器），丢失窗口≈0；
  想更保险可在部署前于登录后 curl 一次 `POST /api/admin/snapshot`（管理员）。
- 回滚 = 用上一版代码再部署一次（数据始终在挂载盘，不动）。控制台也有版本/流量切换。

## 访问入口（共享域名 `/weibo` 子路径）

正式入口 **`https://<你的备案域名>/weibo/`**：域名在云开发控制台「自定义域名」上配了
按路径路由——`/weibo` → `weibo-archive`，其余路径 → 同域名下的其他服务。
网关转发时**保留前缀**，容器侧靠 `WEIBO_BASE_PATH=/weibo`（已固化在 Dockerfile）适配：

- HTML 里的 `__WB_BASE__` 占位被注入成 `/weibo`，前端接口与图片请求自动挂前缀；
- 后端把带前缀的请求剥掉再路由（网关将来改为剥前缀也同样能跑）；
- 会话 cookie 的 `Path=/weibo/`，不会发给同域其他服务。

**换独立子域名根路径 = 把 `WEIBO_BASE_PATH` 置空重新部署，零代码改动。**
默认测试域名也随之只能走 `https://<默认域名>/weibo/`（根路径 401 属预期）。

## 配置 AI 归档（部署后必做，一次）

归档不再依赖 claude/Node/MCP（ADR-0012）：管理员登录网页 → 「管理」→ **AI 归档服务**
一行，点「添加服务」填三项（中转服务地址 / 密钥 / 模型名）保存即可。可添加多家并上移
下移/停用/删除，列表顺序即优先级（第一个为主用）：每次归档从主用起依序现试，任一失败
自动换下一家（ADR-0013）。密钥只存掩码显示，界面与日志永不回显原文。一家都没配齐（或
全部停用）时用户点【同步】会提示「AI 归档功能还没开通」。

## 数据备份下载

管理后台「数据备份 → 下载完整备份」把线上整库另存一份到本地（吐的是挂载盘上的快照文件，
不碰运行库；支持断点续传，60s 网关超时下也能下完大库）。控制台存储里下载 `weibo/weibo.db`
是同一份数据的备用通道。

## 验证清单（每次部署后）

```bash
# 正式入口：200 + 注入前缀 = 新版页面
curl -s https://<你的备案域名>/weibo/ | grep -o "var WB_BASE = '[^']*';"
# 应返回 401「请先登录」（说明打到本服务而非同域其他服务）
curl -s https://<你的备案域名>/weibo/api/state
```

> 默认测试域名形如 `https://weibo-archive-<一串账号相关编号>.sh.run.tcloudbase.com/weibo/`
> （控制台服务详情里查；仅调试备用，同样要走 `/weibo/`）

- 网页：登录 → 列表有数据 → 博主增量拉取一条能跑 → 管理员「AI 归档服务」配置在 →
  挑一条【同步】能出语雀文档。
- 持久化：管理后台随便改点东西（如博主排序）→ 等 5 分钟 → 控制台存储里
  `weibo/weibo.db` 的修改时间应更新 → 重新部署后改动仍在。

## 计费与运维备忘

- 常驻 1 副本约 0.055/(核·h)+0.032/(GB·h)：0.25核0.5G ≈ 0.02 元/小时 ≈ **14 元/月**，
  在个人版 4 万资源点内绰绰有余；不够买资源包 10 元/万点。
- 日志：控制台 云托管 → 服务 → 日志（或 `cloudbase cloudrun log -s weibo-archive`）。
- 432 反爬暂停、定时拉取补偿等行为与旧服务器完全一致。
- ⚠️ 快照最长滞后 5 分钟：如果实例被**强杀**（非正常下线），最多丢最近 5 分钟的写入。
  可接受；重要操作（大批量覆盖更新）后手动 `POST /api/admin/snapshot` 一次即可。
- 域名：可与个人已有备案域名共用（按路径路由，见「访问入口」节）；若用独立子域名，
  置空 `WEIBO_BASE_PATH` 重新部署即可，零代码改动。
